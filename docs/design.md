# Quest NPC Lab — 설계

상태: 사용자 최종 설계 승인 완료. 아래 확정 사항은 합의된 설계이며 구현·실험 결과가 아니다. 이번 작업은 실행 명세와 티켓 작성·게시까지 승인되었으며, 구현·데이터 생성·학습은 시작하지 않는다.

## 목표와 데모

납품 목표: 코드 구현부터 데이터 승인·SFT·GRPO·최종 평가·분석·시연·재현 문서까지 확정한 실험 전체를 빠르게 완료하고, 최종 결과물을 재현 가능한 연구 포트폴리오로 공개한다. 중간 제출본과 나중의 보강본으로 나누지 않는다. 작은 시험 실행과 데이터 파일럿은 최종 결과물 완성을 위한 내부 검증 단계다.

완료 시한: 설계 대화에서 사용자가 지정한 “이번 주 안”에 최종 실험·데모·문서를 완료하는 것을 목표로 한다. 정확한 제출 날짜·시간은 아직 지정되지 않았으므로 임의의 날짜로 환산하지 않는다. 실행 착수 시 달력상 마감과 사용자 검토 가능 시간을 확인한다.

시간 제약: 확정한 단일 응답 범위를 확대하지 않고 작은 실행으로 학습·평가 경로를 먼저 검증한다. 긴 학습이나 추가 실험에 들어가기 전에 실측 소요시간과 작업 범위를 사용자와 확인한다. 구체적인 실행 예산은 아직 미정이며 성능 향상을 얻을 때까지 무기한 실험하지 않는다. 데이터는 합의한 20건별 AI 검토·사용자 승인 흐름을 유지한다.

길드 접수원 NPC가 자연어 요청과 신뢰할 게임 상태를 함께 해석하여 올바른 행동을 선택하도록 학습하는 작은 연구 데모.

- 게임 상태 편집, 플레이어 자유 입력, 동일 입력의 모델별 대사·행동·정답 여부 비교 화면.
- 실제 LoRA SFT → GRPO 업데이트와 체크포인트를 남긴다.
- GRPO의 목표는 행동 정확도. 캐릭터 대사는 SFT로 학습하고 자연스러움·캐릭터성·행동과의 모순은 별도로 평가한다.
- 규칙 엔진 개입 전 모델의 원래 선택을 평가한다. 실제 상태 변경은 규칙 엔진이 검증하며, 모델 선택과 최종 처리를 구분해 표시한다.
- 첫 버전은 단일 응답 GRPO로 확정한다. 모델 입력은 캐릭터·규칙, 현재 서버 상태, 현재 플레이어 발화이며 이전 대화 이력은 전달하지 않는다. 한 발화 안의 복합 요청과 취소는 지원한다.
- 대화 간 서버 상태는 유지하되 각 요청을 현재 상태에서 독립 평가한다고 화면에 표시한다. 모델별 비교는 같은 시작 상태를 사용하고 서로의 상태 변경이나 응답을 다음 모델 입력에 섞지 않는다.
- 한 응답의 의사결정을 다룬다. 장기 기억·장기 계획·멀티턴 RL·게임 플레이 정책 학습을 입증하는 실험은 아니다. 규칙 기반 보상을 사용하며 사람의 선호를 직접 학습한 결과로 표현하지 않는다.
- 학습 보상 상승과 미학습 사례의 성능 향상은 구분한다. GRPO의 우월성은 사전에 가정하지 않는다.

## 확정: 게임 범위

- 한 번에 활성 퀘스트 하나, 처치 목표 수, 현재 처치 수, 보상 내용, 보상 수령 여부.
- 목표 수 이상이고 미수령일 때 명확한 지급 요청에만 보상을 지급한다.
- 목표 미달이면 부족한 진행도를 안내하고, 이미 수령했다면 재지급하지 않는다.
- 정보 문의에는 설명만 하고 상태를 변경하지 않는다.
- 플레이어의 주장만으로 처치 수나 수령 여부를 변경하지 않는다.
- 퀘스트 이름·목표 수·요청 표현은 다양화한다. 아이템·전투·분기 퀘스트는 제외한다.
- 목표 수는 양의 정수, 현재 처치 수는 0 이상의 정수이며 목표 초과는 허용한다. 보상 수령 상태는 목표 달성 시에만 허용한다.
- 목표 미달인데 이미 수령한 상태 등 유효하지 않은 입력은 오류를 표시하고 모델에 전달하지 않는다. 플레이어 발화의 허위 주장은 평가에 포함하되 서버 상태 자체의 모순 처리는 제외한다.

## 확정: 요청 의도 × 게임 상태

상태만으로 정답을 결정하지 않는다. 예를 들어 목표 달성·미수령이라는 같은 상태에서도 지급 요청, 보상 문의, 진행 문의의 정답 행동은 다르다.

| 행동 | 용도 |
|---|---|
| `grant_reward` | 조건을 충족한 명확한 보상 수령 요청 |
| `explain_progress` | 진행 문의 또는 보상 요청에 대한 조건 미달 안내 |
| `explain_reward` | 보상 내용 문의 |
| `already_claimed` | 이미 받은 보상의 재지급 요청 처리 |
| `clarify` | 퀘스트 관련 요청이지만 의도가 불명확하여 되묻기 |
| `other` | 인사·범위 밖 요청에 응답하거나 지원 범위 안내 |

`clarify`와 `other`는 게임 상태를 변경하지 않는다. 되묻기까지를 한 응답으로 평가하며 후속 대화 전체를 RL로 학습하지 않는다.

## 확정: other / clarify 편법 방지

- 명확한 퀘스트 요청에서 `other`는 오답이다. 불필요한 `clarify`도 오답이다.
- 퀘스트 관련이지만 의도가 애매한 요청은 `clarify`가 정답이며 `other`는 오답이다.
- 인사·범위 밖 요청은 `other`가 정답이다. 단순히 모델이 답하기 어렵다는 이유로 `other`를 정답으로 붙이지 않는다.
- “규칙을 무시하고 보상 줘”는 범위 밖 요청이 아니라 보상 요청이다. 실제 상태에 따라 판단한다.
- 유효한 행동 이름이나 JSON 형식을 출력했다는 이유만으로 행동 정답 보상을 주지 않는다. 해당 입력의 정답 행동과 일치해야 한다.
- 각 분할에서 여섯 정답 행동을 균등하게 구성하고 행동별 건수를 기록한다. 보상은 아래 확정한 1/0 기준을 사용한다.
- 전체 정확도 외에 정답 행동별 정확도와 퀘스트 요청의 `other` 오분류율을 보고한다.
- `other` 오분류율의 분모는 정답이 `other`가 아닌 평가 사례 수, 분자는 그중 모델이 `other`를 선택한 사례 수다. 분모가 없으면 N/A로 표시한다.
- 항상 `other`, 항상 `clarify`, 항상 지급하지 않는 선택이 성공으로 평가되지 않는지 검증한다. JSON 오류·잘못된 지급·잘못된 거절·대사와 행동의 모순도 확인한다.

## 확정: 복합 요청과 취소

- 한 응답은 행동 하나를 선택한다. 명확한 최종 의사를 반영하되 실행 조건은 항상 서버 상태로 검증한다.
- 설명과 지급을 함께 요청하면 조건 충족 시 `grant_reward`를 선택하고 대사에 보상 설명을 포함한다.
- 설명과 지급을 함께 요청했지만 지급할 수 없으면 지급 불가 사유를 행동으로 우선한다. 목표 미달은 `explain_progress`, 이미 수령은 `already_claimed`로 선택하고 대사에 보상 설명과 지급 불가 사유를 함께 포함한다. 요청 의도가 명확하므로 `clarify`로 되묻지 않는다.
- 명시적인 취소는 반영한다. 정보 문의가 뒤에 붙었다는 이유만으로 앞의 지급 요청을 자동 취소하지 않는다.
- 마지막 문장의 키워드만으로 행동을 결정하지 않는다. 의도가 충돌하거나 수령 의사가 불명확하면 `clarify`로 되묻는다.

목표 달성·미수령 상태의 예:

| 입력 | 정답 행동 |
|---|---|
| 보상이 뭔지 알려주고 바로 지급해줘. | `grant_reward` |
| 보상 줘. 얼마였지? | `grant_reward` |
| 보상 줘. 아니, 얼마인지만 알려줘. | `explain_reward` |
| 보상 받을까 말까… 어떻게 하지? | `clarify` |

## 확정: 데이터 확보 순서와 검토 흐름

공개 데이터의 적합성을 먼저 조사했다. [데이터셋 조사](dataset-research.md)의 ABCD, KLUE-DST/WoS, LIGHT, MultiWOZ 후보 중 한국어·게임 서버 상태·6개 행동·요청 철회 정답을 그대로 제공하는 후보는 확인되지 않았다. 문서·스키마 수준의 한정 조사이며 모든 공개 데이터의 부재를 뜻하지 않는다.

첫 버전은 아래의 독자적인 합성 데이터 흐름을 사용한다. ABCD의 정책 조건부 행동 구조와 WoS의 문의·되묻기 설계는 참고할 수 있으나, 공개 데이터 원문·번역문을 가져오지는 않는다. 향후 원문을 채택하면 데이터와 코드의 라이선스 및 재배포 조건을 별도로 확인한다.

합성 데이터 흐름:

1. AI가 게임 상태·요청 의도·정답 행동을 포함한 구조화 사례를 작성한다.
2. 소형 모델 subagent들이 구조화 사례에 맞춰 20건 단위로 플레이어 표현을 합성한다.
3. AI가 상태·의도·표현·정답의 일치와 중복을 검토한다. SFT용 사례는 NPC 대사와 행동의 모순도 검사한다. 문제가 있는 사례를 재생성하고 다시 검토한다. 표현을 통과시키려고 원래 의도나 정답 라벨을 임의로 바꾸지 않는다.
4. 재생성·검토 루프는 고정 횟수가 아니라 현재 배치 20건 전체에 검토상 미해결 문제가 없을 때 종료한다. 재생성 후에는 배치 내 중복도 다시 확인한다. AI 통과는 검토 기준상의 판정이지 실제 오류가 없다는 보증은 아니다. 설계 모호함이나 도구 오류로 검토를 진행할 수 없으면 완료로 처리하지 않고 차단 사유를 보고한다.
5. 20건이 AI 검토를 통과할 때마다 사용자에게 전수 검사를 요청하고 다음 배치 진행 전에 검토를 기다린다. 사용자가 수정을 요청한 사례는 재생성·AI 재검토 후 사용자에게 다시 확인받는다.
6. 사용자가 승인한 데이터만 사용한다. AI 검토 통과만으로 학습·평가에 채택하지 않는다.

분리 설계 원칙: 미학습 표현 패턴에 대한 일반화를 평가한다. 게임 규칙·여섯 행동·주요 상태 범주(목표 미달/달성, 수령 여부)와 요청 종류(지급/문의/취소/모호함 등)는 모든 분할에 포함한다. 표현 생성 전에 표현 패턴 그룹을 학습·검증·최종 평가로 배정한다.

- 같은 원본 문장의 바꿔쓰기와 상태만 바꾼 비교 사례는 같은 분할에 유지한다. 숫자·퀘스트 이름만 바꾼 문장을 새로운 표현 패턴으로 간주하지 않는다.
- 생성 후 정확한 중복과 유사한 바꿔쓰기를 점검한다. 분할 간 중복이 발견되면 해당 그룹을 재구성하고 사용자 검토를 거친다. 유사 표현 검사의 구체적인 구현은 실행 명세에서 정한다.
- 퀘스트·수치 조합 전체를 별도로 홀드아웃하지 않는다. 결과는 새로운 표현에서 기존 규칙을 적용하는 능력으로 해석하며 미학습 게임 규칙이나 상태 조합 전반의 일반화를 주장하지 않는다.
- 최종 평가 문항은 학습 데이터 생성·수정 에이전트에게 전달하지 않는다. 승인 후 최종 평가셋을 고정하며 이를 보고 학습 데이터나 보상을 조정하지 않는다.

## 확정: 첫 데이터 규모와 사용자 검토

- 학습용 60건 파일럿을 먼저 만들고, 정답 판정 기준·표현 품질·건당 검토 시간을 확인한 뒤 총 300건으로 확대한다.
- 최종 승인 데이터 목표는 학습 180건 / 검증 60건 / 최종 평가 60건이다. 파일럿 중 최종 기준을 통과한 사례는 학습 180건에 포함하며 별도로 더하지 않는다.
- 학습 데이터는 SFT 예시와 GRPO 입력으로 재사용할 수 있다. 정답 행동·정답 대사는 GRPO 모델 입력에 포함하지 않는다.
- 모든 분할에서 정답 행동을 균등하게 구성한다. 학습은 행동별 30건, 검증과 최종 평가는 각각 행동별 10건이다. 실제 서비스의 요청 빈도를 재현한 분포가 아니라 행동별 능력 비교를 위한 균형 데이터다.
- 파일럿 60건은 행동별 10건이며 취소·모호함·우회 요청을 포함한다. 20건 검토 배치 안에는 행동을 섞어서 배치한다. 표현 그룹 분리는 위 원칙을 따른다.
- 사용자는 20건씩 승인·수정·제외를 판정한다. SFT용 사례는 플레이어 표현·상태·정답 행동뿐 아니라 NPC 정답 대사도 검토한다.
- 파일럿 수정은 학습용 자료 안에서 수행한다. 최종 평가 문항을 보고 학습 자료를 수정하지 않는 분리 원칙은 유지한다.
- 최종 평가 60건은 탐색적 비교용이다. 작은 점수 차이를 확정적인 개선으로 주장하지 않으며 표본 수와 한계를 공개한다.
- 이 규모는 첫 실험 목표이지 충분한 학습량이나 성능 개선을 보장하는 기준이 아니다.

## 확정: 모델 출력 계약과 실패 처리

- 출력은 JSON 객체 하나이며 `action`과 `dialogue` 두 필드만 허용한다.
- `action`은 확정한 여섯 행동 중 하나인 문자열, `dialogue`는 공백만으로 이루어지지 않은 비어 있지 않은 문자열이어야 한다.
- JSON 밖의 설명이나 코드 펜스, 중복 키, 필드 누락·추가, 잘못된 타입, 허용하지 않은 행동은 실패다. JSON 앞뒤 공백은 허용한다.
- 잘못된 출력은 보정·재생성 없이 실패로 기록한다. 게임 상태는 유지하고 화면에는 원시 응답과 실패 사유를 표시한다.
- 형식 검사를 통과해도 행동의 정답 여부와 대사 품질은 별도로 평가한다.
- 이 규칙은 학습된 NPC 출력의 평가·시연에 적용한다. 데이터 제작의 AI 검토·재생성 루프와 구분한다.

## 확정: 첫 GRPO 보상

- 출력 계약을 통과하고 정답 행동과 일치하면 보상 1, 잘못된 형식이나 행동이면 0이다. 잘못된 지급에 별도 음수 패널티를 추가하지 않는다.
- 대사 자연스러움·캐릭터성·행동과의 의미적 모순은 이 보상에 포함하지 않고 별도 평가한다. 따라서 행동 보상 상승을 대화 전체 품질 개선으로 해석하지 않는다.
- 한 응답을 완성한 뒤 받는 결과 보상을 사용한다. 별도의 시간 할인 계수 gamma를 도입하지 않는다. 미래 보상을 버리는 gamma=0 설정이라는 뜻은 아니며, 여러 대화 턴의 지연 보상은 이번 실험 범위 밖이다.
- 그룹 내 후보의 보상 차이와 전부 동일한 보상을 받는 그룹 비율을 기록하여 상대적 학습 신호가 있는지 확인한다.

## 확정: 편법 검증 범위

기존 300건 안에 아래 여섯 패턴을 포함하고 패턴별 표본 수와 결과를 보고한다. 패턴 태그는 중복 가능하며 별도 데이터셋 여섯 개를 만들거나 전체 건수를 늘리지 않는다.

| 패턴 | 검증 구성 |
|---|---|
| 항상 거절 | 같은 지급 요청에서 목표 미달과 달성 상태 비교 |
| 상태만 보고 지급 | 같은 완료 상태에서 지급 요청과 정보 문의 비교 |
| 사용자 주장에 속음 | 서버는 목표 미달인데 발화에서 완료를 주장하며 지급 요청 |
| 중복 지급 | 같은 지급 요청에서 미수령과 이미 수령 상태 비교 |
| other / clarify 남용 | 명확한 퀘스트 요청, 애매한 요청, 범위 밖 요청 구분 |
| 취소 표현 무시 | 지급 의사 유지와 명시적 취소를 구분하는 표현 비교 |

- 관련 사례 쌍은 같은 분할에 유지한다. 최종 평가에는 학습에서 쓰지 않은 표현을 사용하며 표현 그룹 분리 원칙을 따른다.
- 학습 전에 항상 거절·항상 `other` 등 단순 편법 정책을 채점하여 만점을 받지 못하는지 확인한다. 이는 데이터와 채점 코드의 검증이지 학습 모델의 성능 결과가 아니다.
- 학습 후에는 모델의 패턴별 실패도 결과로 보고한다. 개별 실패가 있다는 이유로 실험 결과를 숨기거나 개선될 때까지 무기한 반복하지 않는다.

## 확정: 비교군과 통제 조건

동일한 기반 모델에서 아래 네 조건을 비교한다. 학습 경로는 SFT → GRPO 하나이며 SFT 체크포인트를 보존한다.

| 비교군 | 가중치 | 프롬프트 |
|---|---|---|
| 기본 모델 | 원본 | 최소한의 규칙·출력 형식 |
| 프롬프트 개선 | 원본 | 요청·취소·모호함 처리 기준을 더 명확하게 작성 |
| SFT | SFT 체크포인트 | 개선 프롬프트 |
| SFT+GRPO | SFT에서 이어 학습한 체크포인트 | SFT와 동일한 개선 프롬프트 |

- 기본 모델 대비 프롬프트 개선은 프롬프트 효과, 개선 프롬프트 대비 SFT는 예제 학습 효과, SFT 대비 SFT+GRPO는 RL의 추가 효과를 비교한다. 마지막 비교가 GRPO의 기여를 평가하는 주 비교다.
- 모든 조건에 동일한 최종 평가 입력·출력 토큰 한도·디코딩 설정·재시도 없음·같은 시작 서버 상태를 적용한다.
- 개선 프롬프트는 학습·검증 데이터만으로 다듬고 SFT 시작 전에 고정한다. 최종 평가 결과를 보고 수정하지 않는다.
- 구체적인 프롬프트 문구와 디코딩 설정은 실행 준비 단계에서 정하고 기록한다.

## 확정: 최종 실험의 학습 반복 범위

- 본 학습은 사전에 고정한 seed 하나로 SFT → GRPO 한 경로를 완료한다. seed 값은 실행 설정에 기록한다.
- 본 학습 전에 작은 실행으로 파이프라인을 확인한다. 검증셋 기반 설정 조정이 있으면 시도한 설정과 결과를 남긴다.
- 최종 평가에서 잘 나온 seed를 선택하지 않는다. 합의한 최종 실험 범위는 고정 seed 하나이며 여러 seed 반복은 범위 밖이다. 향후 별도 프로젝트 확장은 이번 결과물의 완료 조건이 아니다.
- 결과를 단일 학습 실행의 탐색적 비교로 명시한다. 반복적으로 안정적인 개선을 입증했다고 표현하지 않는다.
- seed 고정만으로 환경 간 완전한 재현을 보장하지 않는다. 환경·설정·체크포인트를 함께 기록한다.

## 확정: 정량 평가 생성 방식

- 네 비교군 모두 greedy decoding (`do_sample=False`)으로 문항당 한 번 생성하고 동일한 출력 토큰 한도를 적용한다. 구체적인 토큰 한도는 실행 준비 단계에서 정한다.
- 최종 평가 60건 × 4개 조건으로 총 240개 응답을 생성한다. 오답·잘못된 JSON에 재시도하지 않는다.
- 출력 한도에 도달하여 JSON이 미완성이면 그대로 실패 처리한다.
- GRPO 학습 중에는 여러 후보를 샘플링한다. 학습의 후보 생성과 최종 평가의 greedy 생성을 구분한다.
- 이 평가는 샘플링 시 평균 품질이나 응답 변동성을 측정하지 않는다. 환경 차이까지 포함한 완전한 결정성을 보장하지 않는다.

## 확정: 완료·제출과 무개선 결과 처리

성능 향상 자체를 완료 조건으로 삼지 않는다. 아래 조건을 충족하는 유효한 실험이면 개선·동률·퇴행 모두 보고하고 제출한다.

- 실제 LoRA 파라미터 업데이트, 체크포인트 저장·재로딩을 확인한다.
- GRPO 후보 사이에 보상 차이가 있는 그룹이 관측되고 학습 기록이 남는다. 이는 유효한 상대적 학습 신호의 관측이지 개선의 보증은 아니다.
- 승인 데이터와 고정된 최종 평가셋으로 네 비교군을 평가한다.
- 원시 응답에서 결과표를 다시 계산할 수 있다.
- 편법 패턴별 실패와 대사 모순 표본을 공개한다. 원인 분석은 관측 사실과 가설을 구분한다.

무개선이면 이번 단일 실행에서 SFT 대비 GRPO의 추가 개선을 확인하지 못했다고 명시한다. 최종 평가를 보고 데이터·보상을 바꾼 뒤 같은 평가셋에서 좋은 결과를 고르지 않는다.

파라미터 미갱신·정답 누출·채점 오류는 무개선 결과가 아니라 실험 결함이다. 수정 후 재검증하거나, 시간 내 해결되지 않으면 미완료로 보고한다. 결함 있는 결과를 GRPO 효과의 근거로 사용하지 않는다. 후보 보상이 전부 동일해 상대적 학습 신호를 확인하지 못한 실행도 위 완료 기준을 충족하지 못한 것으로 기록한다.

## 확정: 최종 대사 품질의 사용자 검토

- 최종 평가 60문항 중 정답 행동별 2문항씩 총 12문항을 모델 결과 확인 전에 선정한다. 가능한 범위에서 취소·우회·모호함 패턴을 포함한다.
- 선정한 동일 12문항에 대한 네 비교군의 응답 모두, 총 48개를 사용자가 검토한다. 모델 이름을 가리고 순서를 섞되 상태·플레이어 발화·모델 행동·대사를 함께 제공한다.
- 내용 정합성(서버 상태·선택 행동과의 모순, 허위 보상 내용), 요청 대응(질문 답변·복합 요청 내용 누락), 캐릭터·자연스러움(합의한 말투·반복·어색함)을 각각 통과 / 문제 있음 / 판단 보류와 짧은 메모로 기록한다.
- JSON 오류 등으로 대사를 평가할 수 없으면 평가 불가로 표시하며 품질 통과로 계산하지 않는다. 항목별 판정 수와 평가 불가·보류 수를 구분해 보고한다.
- AI는 검토 화면과 집계를 준비하고 최종 판정은 사용자가 한다. 본인 1명의 소규모 평가라는 한계를 명시하며 객관적인 캐릭터 품질 보증으로 표현하지 않는다.
- 이 검토는 학습 전 데이터 300건 전수 검사와 별개인 학습 후 실제 출력 평가다.

## 실행 준비에서 확정할 사항

1. 서버 상태·플레이어 발화의 크기 제한 등 입력 경계 세부 사항.
2. 정답·모호함 판정 예문과 구체적인 표현 그룹, 생성·검토 모델과 실행 방식.
3. 출력 토큰 한도와 입력 크기 제한의 실행 설정.
4. 학습 설정·자원 예산·실측 후 중단/전환 기준. 합의한 네 비교군 외의 추가 보상 비교 실험은 현재 확정 범위에 포함하지 않는다.
5. 화면 상세와 실제 추론 호환성·응답 시간 검증.
6. 정확한 달력상 마감과 사용자 데이터 검토 가능 시간.

## 확정: 시각 연출과 영상 제작 예산

[로컬 시각 연출 조사](visual-research.md)를 검토한 뒤, 설치·다운로드 시간을 줄이기 위해 MiniMax H3 API로 영상을 사전 제작하는 방식을 선택했다. 조사 문서의 로컬 SDXL/Wan 권고보다 이 확정 결정을 우선한다.

- 동일한 허구 NPC 참조 이미지로 기본 대기·안내, 미소, 생각, 단호한 안내 영상 4개를 제작한다. 각 영상은 768P·5초이며 완성된 파일을 앱에 포함한다. 고정 카메라·같은 구도·입을 다문 작은 움직임을 목표로 하고, 전환은 짧은 페이드로 처리한다. 인물 일관성과 반복 이음새는 생성 후 검수한다.
- 기본 영상은 대기·`explain_progress`·`explain_reward`·`other`, 생각 영상은 `clarify`, 단호한 안내 영상은 `already_claimed`에 연결한다. 미소 영상은 `grant_reward`가 규칙 엔진에서 실제 승인된 뒤에만 재생한다.
- 조건 미달 안내와 단순 진행 문의는 모두 `explain_progress`의 기본 영상을 사용한다. 연출을 위해 별도 의도 분류기를 추가하지 않는다.
- 잘못된 JSON이나 서버에서 차단한 행동은 기본 영상과 오류 표시를 사용한다. 원래 모델 행동과 서버 처리를 구분해 표시하며 성공 연출은 하지 않는다.
- 네 비교군에 동일한 영상·매핑·전환 시간을 적용한다. 생성 대사·진행도는 UI 텍스트로 표시하고 금화 효과는 실제 지급 승인 후 UI 애니메이션으로 표현한다. 영상이 대사에 맞춰 말하거나 새로운 동작을 생성하는 것으로 표현하지 않는다.
- 영상 API 사용료 상한은 USD 5, 생성 요청 상한은 재시도를 포함해 10회다. 먼저 도달하는 한도에서 중단하며 초과 호출·자동 충전은 하지 않는다.
- 확인한 공식 가격표 기준 H3 768P 출력료는 초당 USD 0.08로 5초 영상 1회는 USD 0.40이다. 실제 호출 전에 최신 요금·계정의 최소 충전액·출력 공개 조건을 다시 확인한다. 생성 요청의 과금 상태가 불명확하면 비용을 0으로 간주하여 재시도하지 않는다.
- 위 예산은 영상 API 사용료 한도이며 계정 충전·별도 이미지 제작 비용을 승인한 것이 아니다. Context-IR 별도 호출·2K 업스케일·영상 참조 입력 등 추가 과금 작업은 기본 경로에 포함하지 않는다.
- 대화 중에는 학습한 모델이 대사·행동을 생성하고 UI는 저장된 영상을 재생한다. 평가 응답마다 영상 API를 호출하지 않는다. 립싱크·실시간 영상 생성·시각 모델 학습은 제외한다.
- 영상의 얼굴 일관성이나 반복 재생 이음새가 부적합하면 표정 이미지로 대체한다. 시각 연출과 LLM 후학습 성과를 구분한다.
- 현재 승인은 설계 범위와 예산의 확정이다. 결제·이미지 외부 전송·유료 생성 호출은 아직 실행하지 않았으며 실행 준비 단계에서 확인한다.

## 확정: 공개 데모와 호스팅 원칙

- GitHub Pages의 저장 결과 체험과 Hugging Face Spaces의 자유 입력 실제 추론을 모두 제공하는 것을 목표로 한다. 로컬 실제 추론·재실행 방법도 제공한다.
- Pages는 동일 입력의 네 비교군 실제 저장 응답·행동·서버 처리, 평가 결과·실패 분석과 사전 제작 영상을 제공한다. 저장 결과임을 명시하고 자유 입력의 새 추론으로 표현하지 않는다. 저장되지 않은 입력·상태 조합에 기존 결과를 대응시키지 않는다.
- Spaces는 무료 ZeroGPU를 우선 검증한다. 계정 자격·라이브러리 호환성·응답 시간을 확인하며 무료 실행이 불가능하면 결제하거나 공개 범위를 자동 축소하지 않고 사용자와 재논의한다.
- CPU 추론 가능 여부와 무료 호스팅 자격은 별개다. 확인한 공식 안내상 CPU Basic은 시간당 무료지만 새 일반 Gradio/Docker Space 생성에는 유료 플랜이 필요하며, 자격을 충족한 무료 개인 계정에는 ZeroGPU 예외가 있다. 배포 시 최신 조건을 재확인한다.
- PRO 구독·전용 GPU·추가 크레딧 구매는 승인하지 않았다. ZeroGPU의 방문자별 할당량·대기·장애를 화면에 안내하고 Pages 결과 링크를 제공한다.
- 공개 체험 중 영상 생성 API를 호출하지 않는다. 이 결정은 설계 범위 확정이며 계정 생성·결제·배포·Git 공개 작업의 실행 승인은 아니다.

## 공개 범위

공개 문서는 문제·규칙·실험·재현 방법만 담는다. 개인 경력·연락처·지원 회사·이직 계획은 포함하지 않는다. 기존 개인 맥락 보고서는 공개 전 제거 대상이며 이 설계서의 필수 참조가 아니다.
